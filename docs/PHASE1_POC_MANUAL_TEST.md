# Phase 1 PoC 手動検証手順

更新日: 2026-08-08

## 1. 目的

Windows 11実機で次を確認する。

- マイクとPC再生音声を別のWAVへ保存できる
- 2つの音声レベルメーターが独立して動く
- 選択ウィンドウの意味のある変更時だけPNGが保存される
- 一部Captureが失敗しても他の記録が継続する
- 会議終了後にWAVとJSONが正常に確定する

この手順では実際のマイク音声と、選択した出力デバイスの全再生音声をローカル保存する。機密会議ではなく、テスト用の音声と画面を使用すること。

## 2. 起動前確認

PowerShellでPythonプロジェクトへ移動する。

```powershell
cd summarize-meeting
uv sync
uv run ruff check .
uv run pytest -q
```

テストが成功したらアプリを起動する。

```powershell
uv run summarize-meeting
```

## 3. 2分スモークテスト

### 3.1 入力

1. 会議名へ `Phase1_2分テスト` と入力する。
2. 実際に声を入力できるマイクを選択する。
3. テスト音声を再生するスピーカーと同名のPC音声を選択する。
4. テスト用のPowerPoint、ブラウザ、テキストエディタなどを取得画面として選択する。
5. 保存先にアプリ配下の `data/meetings` が表示されていることを確認する。
6. 「会議開始」を押し、保存先表示が作成されたセッションフォルダへ切り替わることを確認する。

### 3.2 録音中

1. 状態行に選択したマイク名が表示されていることを確認し、マイクへ10秒程度話してランプが緑、メーターが動くことを確認する。
2. 状態行に選択したPC音声デバイス名が表示されていることを確認し、PCでテスト音声を10秒程度再生してランプが緑、メーターが動くことを確認する。
3. 状態行に取得対象ウィンドウ名が表示されていることを確認し、取得画面の内容を大きく切り替える。
4. マウスだけを30秒程度動かし、保存画像数が急増しないことを確認する。
5. 対象ウィンドウを最小化し、画面ランプが黄色になることを確認する。
6. 対象を復元し、画面ランプが緑へ戻ることを確認する。
7. 約2分後に「会議終了」を押す。
8. 入力、開始、終了、更新、画面再選択がすべて無効になることを確認する。
9. 保存処理の進捗バーが表示され、画面停止、音声停止、書込み待ち音声の保存、音声ファイル結合、検証、セッション情報保存の段階が確認できることを確認する。
10. 進捗率が後戻りせず100%へ到達した後、保存完了メッセージへ切り替わり、進捗バーが非表示になることを確認する。

### 3.3 保存物

画面に表示された保存先を開き、次を確認する。

```text
session.json
events.jsonl
logs/session.log
audio/microphone.wav
audio/system.wav
audio/manifest.json
screenshots/events.jsonl
screenshots/*.png
```

確認項目:

- `microphone.wav` と `system.wav` をそれぞれ再生できる
- マイクの発話は主に `microphone.wav` に入っている
- PCテスト音声は `system.wav` に入っている
- WAVの長さが約2分である
- `audio/manifest.json` に `monotonic_origin_ns` と各trackの `estimated_start_offset_ms` がある
- 各trackの `audio_duration_ms`、`active_capture_duration_ms`、`duration_drift_ms` が数値である
- 通常録音では `overflow_count` が0である
- `max_queue_usage_ratio` が0.0から1.0の範囲である
- `session.json` のstatusが `RECORDED` である
- `duration_ms` が実際の録音時間と大きく違わない
- `logs/session.log` が1行1JSONで読み取れ、最後の `session_finished` にAudio診断と画像件数がある
- `logs/session.log` に入力した会議名、選択デバイスID・名称、画面タイトル、PCM値、発言内容、画像内容が含まれない
- 画面切替後のPNGが存在する
- マウス移動だけのPNGが大量に存在しない

### 3.4 録音準備中の応答性とキャンセル

開始に時間がかかるテスト用Audioデバイスを利用できる場合に実施する。

1. 「会議開始」を押した直後に「録音デバイスを準備しています」と表示され、ウィンドウの移動や再描画が継続することを確認する。
2. PREPARING中は入力・開始・更新・画面選択が無効で、「会議終了」だけが有効であることを確認する。
3. 「会議終了」を押し、アプリを強制終了せず開始キャンセルが完了することを確認する。
4. `session.json` が `FAILED_TO_START` となり、warningに `SESSION_START_CANCELLED` があることを確認する。
5. `events.jsonl` に `session_start_cancel_requested` と `session_start_cancelled` が順に記録されることを確認する。

## 4. 部分障害テスト

機密データを使用しない状態で実施する。

### 4.1 対象ウィンドウ終了

1. 録音を開始する。
2. 選択した画面対象を閉じる。
3. 画面ランプだけが赤になり、マイクとPC音声が緑のまま継続することを確認する。
4. 一覧を更新して別ウィンドウを選び、「録音中に画面を再選択」を押す。
5. 画面ランプが緑へ戻り、新しい初回画像が保存されることを確認する。

### 4.2 片方のAudio開始失敗

利用できないデバイスを再現できる環境だけで実施する。

1. マイクまたはPC音声の片方が開始できない状態にする。
2. 確認ダイアログなしで、正常な側の録音が開始することを確認する。
3. 失敗側が赤ランプ、正常側が緑ランプになることを確認する。
4. 会議終了後、正常側のWAVが確定されていることを確認する。
5. マイクとPC音声の両方が開始できない状態でもう一度開始する。
6. 録音中へ遷移せずエラーが表示され、作成された `session.json` の状態が `FAILED_TO_START` になることを確認する。

### 4.3 異常終了後の復旧

この試験ではテスト用セッションを意図的に異常終了させる。通常の会議データでは実施しない。

1. マイクまたはPC音声を選択し、テスト録音を開始する。
2. 70秒以上録音し、少なくとも1つのWAV segmentが作られるまで待つ。
3. WindowsのタスクマネージャーからPoCのPythonプロセスを終了する。
4. `audio/.work/` が残っていることを確認する。内容を変更・削除しない。
5. `uv run summarize-meeting` でアプリを再起動する。
6. 「中断セッションが見つかりました」で復旧を選択する。
7. 元の `audio/.work/` が保持されていることを確認する。
8. `audio/microphone.recovered.wav` または `audio/system.recovered.wav` を再生できることを確認する。
9. `session.json` が `INTERRUPTED` となり、`recovery` に復旧結果が記録されることを確認する。

finalize中断を再現できる場合は、完成済みの最終WAVと `.work` が両方残った状態で復旧する。`session.json` の `recovery.tracks[].source` が `final_wav` となり、同じtrackの `.recovered.wav` が重複生成されないことを確認する。最終WAVを破損させる試験は必ずテストデータのコピーで行い、検証失敗warningとsegment復旧へのフォールバックを確認する。

### 4.4 音声デバイスの再接続

安全に抜き差しできるUSBマイクまたはテスト用仮想Audioデバイスで実施する。業務会議中には行わない。

1. マイクとPC音声の両方を選択して録音を開始する。
2. テスト対象の片方だけを切断する。
3. 対象ランプが黄色の「再接続中」になり、もう片方は緑のまま録音を継続することを確認する。
4. 約10秒以内に同じデバイスを再接続する。
5. 対象ランプが緑へ戻ることを確認する。
6. 会議終了後、再接続前後の音声が同じtrackのWAVに含まれることを確認する。
7. `audio/manifest.json` の対象trackに `gaps` があり、`outcome` が `reconnected` であることを確認する。
8. 別の試行ではデバイスを外したままにし、約10秒後に対象ランプが赤になることを確認する。
9. 再接続を断念しても、もう片方のAudioと画面取得が継続することを確認する。

### 4.5 Windows Graphics Capture

機密情報を表示していないテスト用ウィンドウで実施する。

1. テスト用ウィンドウを取得対象にして録音を開始する。
2. 対象の上へ別ウィンドウを重ね、保存PNGへ重ねた側の内容が混入しないことを確認する。
3. 対象を横長、縦長へリサイズし、変更後のPNG寸法が追従することを確認する。
4. 対象を最小化し、画面ランプが黄色になり、同じ画像が増え続けないことを確認する。
5. 対象を復元し、画面ランプが緑へ戻って新しい変更が保存されることを確認する。
6. 可能なら対象をDPIの異なるモニターへ移動し、画像の欠け、余白、拡縮崩れがないことを確認する。
7. 対象を閉じ、画面ランプだけが赤になって音声録音が継続することを確認する。

対話デスクトップ上で自己ウィンドウ統合テストだけを実行する場合:

```powershell
$env:SUMMARIZE_MEETING_RUN_WGC_TESTS = "1"
uv run pytest -q tests/integration/test_wgc_backend.py
```

### 4.6 保存先の空き容量不足

実際の業務会議ではなくテスト用データで実施する。容量を消費する巨大ファイルは作成せず、テスト専用の閾値注入または空き容量を制限できるテストドライブを使用する。

開始前:

1. 保存先の空き容量が5 GiB未満と判定される条件にする。
2. 会議開始を押し、「保存先の空き容量が不足しています」と表示されることを確認する。
3. `data/meetings/` に新しいセッションディレクトリが作成されないことを確認する。

録音中:

1. マイク、PC音声、画面を選択して録音を開始する。
2. 監視が閾値未満を返す条件にする。
3. 赤い警告に「画面保存を停止し、音声録音を継続します」と表示されることを確認する。
4. 画面ランプが赤になり、それ以降PNGが増えないことを確認する。
5. マイクとPC音声のランプ・メーターが緑のまま継続することを確認する。
6. 画面の再選択を試し、容量不足のため再開できないことを確認する。
7. 会議終了後、WAVが正常に開けることを確認する。
8. `events.jsonl` の `low_disk_space` に `free_bytes` と `minimum_free_bytes` があることを確認する。
9. `session.json` の `session_storage` と `screen` が `FAILED`、warning codeが `LOW_DISK_SPACE` であることを確認する。

### 4.7 設定の保存と破損復旧

1. マイクとPC音声を選択して短いテスト録音を開始し、終了する。
2. `data/settings.json` が作成され、選択した2つのdevice IDが保存されていることを確認する。
3. アプリを再起動し、同じdevice IDのマイクとPC音声が選択されることを確認する。
4. アプリを終了し、テスト対象デバイスを外してから再起動する。
5. 別デバイスへ自動切替されず「なし」のままで、前回デバイスが見つからない案内が表示されることを確認する。
6. アプリを終了し、`settings.json` をテスト用の不正JSONへ置き換える。
7. 再起動後、既定値で画面が開き、設定破損の赤い案内が表示されることを確認する。
8. `data/settings.corrupt-<timestamp>.json` に不正JSONの原本がそのまま退避されていることを確認する。
9. 新しい録音開始後に正常な `settings.json` がatomic保存されることを確認する。

### 4.8 スクリーンショット保存失敗とtemp復旧

テスト専用の保存失敗注入を使用し、実際の会議では実施しない。

1. 画面取得を含むテスト録音を開始し、最初のPNG保存だけを失敗させる。
2. 画面状態が `SCREEN_SAVE_FAILED` の警告を示す一方、画面Captureと両Audioが継続することを確認する。
3. 保存失敗を解除し、「画面保存が復旧しました」と表示され、初回画像が保存されることを確認する。
4. 失敗中のframeでbaselineが進まず、復旧後の画像が欠落しないことを確認する。
5. 別の中断テスト用セッションの `screenshots/` に、正常なPNG bytesを持つ `000001.png.tmp` と不正bytesの `000002.png.tmp` を置く。
6. アプリ起動時の中断セッション復旧を実行する。
7. 正常tempが `000001.png` へ復旧され、不正tempは元の名前・内容のまま残ることを確認する。
8. `session.json` の `recovery.screenshots` に `screenshots/000001.png` があり、不正tempのwarningがあることを確認する。

### 4.9 同じアプリフォルダからの多重起動

1. アプリを起動し、録音画面が表示されたままにする。
2. 同じ配布フォルダの実行ファイルをもう一度起動する。
3. 2つ目のプロセスには「このアプリフォルダのSummarize Meetingは既に起動しています」と表示され、録音画面が開かず終了することを確認する。
4. 1つ目の録音画面が引き続き操作でき、`data/meetings` や `data/settings.json` に2つ目のプロセスによる変更がないことを確認する。
5. 1つ目のアプリを正常終了した後は、同じ実行ファイルを再び起動できることを確認する。

### 4.10 Windows終了要求

業務会議では実施せず、保存していない作業がないテスト用PCまたは仮想環境で実施する。

1. マイクとPC音声を選択してテスト録音を開始する。
2. Windowsのサインアウトまたはシャットダウンを実行する。
3. アプリ独自の終了確認ダイアログが表示されず、Windowsの終了処理を妨げないことを確認する。
4. 次回起動後、終了時間内に確定できた場合は最終WAV、確定できなかった場合は中断セッションの復旧案内があることを確認する。
5. 復旧を実行し、最終WAVまたは `.recovered.wav` が開け、`session.json` に終了結果または復旧結果が残っていることを確認する。

### 4.11 デバイス・ウィンドウ一覧の遅延と部分失敗

テスト用の遅延・失敗注入backendを使用する。

1. マイク一覧だけを2秒遅延させ、「デバイス・ウィンドウを更新」を押す。
2. 一覧取得中もウィンドウの移動や再描画が応答し、アプリがフリーズしないことを確認する。
3. 遅延解除後にマイク、PC音声、画面の候補が表示され、更新・開始操作が復帰することを確認する。
4. マイク一覧だけを失敗させて更新し、PC音声と画面の候補は利用でき、マイク列挙失敗の日本語エラーが表示されることを確認する。
5. 一覧取得を10秒より長く停止させ、timeout案内後に更新・開始操作が復帰することを確認する。
6. timeout後に古い列挙結果を返し、現在の候補や選択が上書きされないことを確認する。

### 4.12 セッションmetadataの一時書込み失敗

テスト専用のrepository失敗注入を使用し、実際の会議データや保存先権限は変更しない。

1. マイクとPC音声を選択して録音を開始する。
2. `events.jsonl` の追記だけを一時的に `OSError` とする。
3. 「セッション情報を保存できません。音声録音を可能な限り継続しています」と1回だけ表示され、両音声メーターとWAV書込みが継続することを確認する。
4. 失敗注入を解除し、別のComponent状態変更を発生させる。
5. `session.json` のwarningに `SESSION_METADATA_WRITE_FAILED` が1件だけ保存されることを確認する。
6. 最終 `session.json` 保存だけを失敗させる試験では、finalize処理が完了してWAVが開け、次回起動時に中断セッションとして復旧できることを確認する。

## 5. 15分テスト

2分スモークテスト成功後に実施する。

- UI操作が継続できる
- 音声メーターが停止しない
- `events.jsonl` に予期しない `AUDIO_CAPTURE_FAILED` がない
- 会議終了後に2つのWAVを開ける
- WAV時間と `duration_ms` の差を記録する
- `audio/manifest.json` のsegment数と最終WAVのframe数を記録する
- 正常終了後に対象trackの `audio/.work/` が削除されていることを確認する
- 2trackの `estimated_start_offset_ms` 差と `duration_drift_ms` を記録する
- `queue_pressure_count`、`max_queue_usage_ratio`、`overflow_count` を記録する
- PNG枚数と合計容量を記録する

## 7. 現在の既知制約

- Windows Graphics Captureの遮蔽、複数モニター、DPI、HDR、保護コンテンツ、Windowsロック、Remote Desktopは実機評価が未完了である。
- 復旧はPCM16 WAV segmentだけを対象とし、元segmentを削除しない。
- スリープ／休止状態はテスト対象外である。
